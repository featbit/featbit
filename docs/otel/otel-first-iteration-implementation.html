01 Prerequisite Shared once

Shared foundation

Task goal

Make FeatBit custom metrics exportable, consistent, and safe for production.

Why

Automatic instrumentation covers infrastructure, but not FeatBit states such as active subscriptions or message drops.

What to measure

Use one custom Meter source per service and identify instances through OTel resource attributes.

Serviceservice.nameMeterInstrument namespace
API server featbit-api FeatBit.Api featbit.api.*
Evaluation server featbit-els FeatBit.EvaluationServer featbit.evaluation_server.*
Control plane featbit-control-plane FeatBit.ControlPlane featbit.control_plane.*
FeatBit.* service.name service.version service.instance.id

Instrument naming

Instrument names follow featbit.<service>.<area>.<name> and the OpenTelemetry naming conventions.

  • Lowercase throughout. Separate namespace components with . and words inside a component with _.
  • Restrict names to letters, digits, _, and .. A service.name value keeps its hyphen (featbit-api), but the <service> component of an instrument name cannot, so use api, evaluation_server, and control_plane.
  • featbit is the application prefix the specification recommends for names private to one application, and the system name that system-specific metrics must start with. Do not repeat it inside <service>.
  • Include <service> only when the area belongs to a single service. Streaming, store availability, and rate limiting are evaluation-server concerns, so they carry the token. Messaging, flag-change propagation, buffers, and workers are emitted by several services and stay service-neutral, so one query spans all of them and service.name supplies the split.
  • Units belong in the instrument's unit argument, not in the name. Drop _ms and _seconds suffixes.
  • Never append _total to a Counter or UpDownCounter.

The instruments that already ship predate this convention. Migrating them is a prefix addition plus a unit-suffix removal.

CurrentTargetUnit
control_plane.consistency.commitsfeatbit.control_plane.consistency.commits{commit}
control_plane.consistency.evicted_commitsfeatbit.control_plane.consistency.evicted_commits{commit}

Renaming an exported metric breaks existing dashboards and alerts, so land the migration in one commit and call it out in the release notes. Meter names are not governed by the semantic conventions and surface as otel.scope.name; keep the existing FeatBit.ControlPlane.Consistency and FeatBit.EvaluationServer.Consistency sources, because the FeatBit.* wildcard exports them either way.

How to implement

  1. Register the relevant Meter with OTEL_DOTNET_AUTO_METRICS_ADDITIONAL_SOURCES. This variable is currently set nowhere in the repository, so the custom meters that already exist—FeatBit.ControlPlane.Consistency and FeatBit.EvaluationServer.Consistency—are silently dropped by the auto-instrumentation. Fix this first; every metric below depends on it.
  2. Register the prefix wildcard OTEL_DOTNET_AUTO_METRICS_ADDITIONAL_SOURCES=FeatBit.* in each service Dockerfile rather than enumerating meters. Auto-instrumentation accepts either an exact source name or a Prefix.* form that registers the entire prefix, so one value covers every existing and future FeatBit.* meter with no further Dockerfile change. This makes the FeatBit. prefix mandatory for every custom meter name.
  3. Create instruments once, then reuse them.
  4. Keep metric attributes finite and exclude identifiers or secrets.
  5. Gauge callbacks read cached or atomic state only .
M1 Required Very low

Streaming connections

Task goal

Show connection demand, current WebSocket capacity, environment-routing load, and connection stability.

Why

One Agent WebSocket can carry updates for many environments, so counting sockets alone can hide load and failure impact.

Term definition

Logical subscription = one active environment route inside ELS

It is a proposed operational counting unit based on the entries managed by DefaultConnectionManager: one mapped Connection tells ELS where to send changes for one environment.

Normal SDK 1 WebSocket → 1 environment route
Agent relay-proxy 1 WebSocket → N environment routes

It does not count flags, evaluations, end users, or the number of SDK processes behind an Agent.

What to measure

MetricWhat it countsProblem it helps reveal
featbit.evaluation_server.streaming.upgrade.requests WebSocket attempts over time, split by result Reconnect storms, validation failures, or rate-limit rejection
featbit.evaluation_server.streaming.sockets.active Accepted physical WebSockets open now Instance capacity, uneven load, or a connection leak
featbit.evaluation_server.streaming.subscriptions.active Active environment routes represented by those sockets Actual fanout load and the blast radius hidden behind Agent sockets
featbit.evaluation_server.streaming.connection.closed Connections closed, split by close outcome Abnormal churn caused by server, client, network, or shutdown
featbit.evaluation_server.streaming.connection.duration How long accepted connections remain open Short-lived connection regressions, proxy timeouts, or unstable networks
M1 answers: Are clients reconnecting? Are instances near connection capacity? How many environment routes depend on each socket? Are connections becoming unstable?

An env.id view is optional and off by default .

How to implement

  1. Record the result as soon as the handshake is decided, including rate-limit rejection.
  2. Maintain socket and subscription totals with atomic deltas in StreamingMiddleware and DefaultConnectionManager.
  3. Count one subscription for a normal socket and the mapped environment count for an Agent socket.
  4. Use try/finally to guarantee decrement; never scan all connections during collection.
M2 Required Low

Messaging and consumers

Task goal

Show whether internal messages are published, waiting, consumed, handled, and acknowledged successfully.

Why

A request may succeed while its asynchronous message later fails, waits in a queue, or reaches a stopped consumer.

Scope

M2 watches the internal server message pipeline

It covers messages exchanged through Kafka, Redis, or PostgreSQL. A logical subscription is an M1 streaming concept and is not measured here.

producer→ broker / queue→ consumer→ handler→ ack / offset

M2 answers whether the asynchronous transport is healthy. M3 adds Flag Change-specific end-to-end propagation.

What to measure

MetricWhat it countsProblem it helps reveal
featbit.messaging.operations Publish, handle, and acknowledgement attempts by outcome Which messaging stage is failing
featbit.messaging.operation.duration Provider delivery or handler time Slow broker, database, or message handler
featbit.messaging.messages.dropped/redelivered Messages known to be lost or delivered again Silent data loss, duplicate processing, or acknowledgement problems
featbit.messaging.queue.depth Number of durable messages waiting Consumer capacity shortage or a stopped consumer
featbit.messaging.oldest_message.age How long the oldest durable message has waited A small number of stuck messages that queue depth may hide
featbit.messaging.consumer.running Whether the consumer task or subscription is active A terminated consumer that no longer emits errors
featbit.messaging.consumer.heartbeat.age Time since the consumer loop or subscription showed liveness A stuck loop or disconnected provider even when traffic is idle
featbit.messaging.consumer.last_success.age Time since a message completed handling Incoming work is no longer being processed successfully
M2 answers: Did publishing fail? Is backlog growing? Is the consumer alive? Were messages lost or replayed? Which stage is slow?

How to implement

  1. Instrument provider adapters rather than every caller.
  2. Treat each provider as two independent transports . The shipped implementations are asymmetric, so provider alone does not describe the delivery guarantee.
  3. Record enqueued, not delivered, until publish confirmation exists .
  4. Poll durable backlog in the background and expose cached values. Expose backlog only where a durable queue exists; the API → ELS Redis direction is Pub/Sub and has nothing to measure.
  5. Count a Kafka handler failure as a known drop. Both consumers call StoreOffset in a finally block regardless of handler outcome, so a failed message is never replayed and the loss is invisible unless handler outcome is recorded separately from consume count.
  6. Update consumer heartbeat independently from message traffic; count loss only when it is known.
M3 Required Low

Flag Change propagation

Task goal

Show whether a saved Flag Change crossed every server-side stage and reached its WebSocket send targets.

Why

The API can return success and sockets can remain connected while clients continue receiving stale configuration.

Failure path to locate

M3 follows one business event across back-end and ELS

It connects generic messaging health to a concrete operational question: “the flag was changed—how far did that change get?”

flag persisted→ MQ published→ ELS consumed→ socket fanout

The required metrics describe aggregate stage health. Optional T1 is used when one specific sampled change must be followed.

What to measure

MetricWhat it countsProblem it helps reveal
featbit.flag_change.operations Success or failure at persist, publish, consume, and fanout A stage gap: saved but not published, published but not consumed, or consumed but not sent
featbit.flag_change.propagation.duration Persistence-to-consume and persistence-to-fanout time Changes eventually arrive but exceed the propagation SLO
featbit.flag_change.fanout.connections Target, successful, and failed socket sends per change Partial delivery: some connected targets receive the change while others fail
featbit.flag_change.config.last_success.age Time since ELS last completed a Flag Change fanout A silently stalled propagation pipeline when new changes are still being published
M3 answers: Was the change saved? Did MQ deliver it? Did ELS consume it? Did any socket sends fail? How long did propagation take?

Server success ends at socket send ; it does not mean that an SDK applied the update.

How to implement

  1. Add a versioned internal message envelope .
  2. Deploy backward-compatible consumers before changing producers.
  3. Measure persistence around the actual flag write and publish success after provider confirmation.
  4. In FeatureFlagChangeMessageConsumer, record one aggregate fanout result per change.
  5. Defer numeric revision lag .
M4 Required Very low

Store availability

Task goal

Show whether ELS can read its configuration data, which provider is serving reads, and whether fallback is stable.

Why

ELS may continue running on a fallback store while the preferred provider is down, slow, or repeatedly recovering and failing.

Term definition

Store = the ELS data source for Flags, Segments, and SDK Secrets

ELS reads these objects through the IStore abstraction. With Redis enabled, HybridStore prefers Redis and can fall back to the configured MongoDB or PostgreSQL database.

ELS read→ IStore→ Redis preferredor MongoDB / PostgreSQL fallback

This Store is not the message queue and not the backend used to store OpenTelemetry data.

What to measure

MetricWhat it measuresProblem it helps reveal
featbit.evaluation_server.store.available Latest health-probe result for each configured provider Redis, MongoDB, or PostgreSQL is unavailable
featbit.evaluation_server.store.selected Which provider currently serves ELS reads ELS has failed over and is operating on a fallback
featbit.evaluation_server.store.last_success.age Time since each provider last passed a probe A provider has been unhealthy for a sustained period
featbit.evaluation_server.store.health_check.operations/duration Probe outcome and elapsed time Timeouts, intermittent errors, or a provider becoming slow before failure
featbit.evaluation_server.store.failover.transitions Changes from one selected provider to another Failover flapping or frequent primary/fallback switching
M4 answers: Can ELS read configuration? Which provider is serving reads? Is ELS running on fallback? Are all providers unavailable? Is failover flapping?

How to implement

  1. Wrap each probe in StoreAvailableSentinel.
  2. Cache the latest result and timestamp for gauge callbacks.
  3. Keep availability and selection separate; count only actual route transitions.
  4. Monitor the sentinel loop through M5 worker metrics.
M5 Required Very low–low

Buffers and workers

Task goal

Show whether in-process work is accumulating, being dropped, flushing successfully, and still being processed by background loops.

Why

The API can remain healthy while buffered records are silently overwritten or a background task has stopped.

Term definition

Buffer holds temporary in-memory work; Worker processes it in the background

A Buffer decouples a fast producer from slower persistence or handling. A Worker is the long-running loop that drains, flushes, consumes, or periodically checks state.

Usage bounded Channel → UsageFlushWorker → database
Insights in-memory List → 1-second flush loop → database
Postgres notification bounded Channel → ELS consumer loop → handler
Store health no buffer → StoreAvailableSentinel loop

These are process-local structures. Unlike a durable MQ queue from M2, their pending contents may disappear when the process stops.

What to measure

MetricWhat it measuresProblem it helps reveal
featbit.buffer.items/capacity Current in-memory item count and configured limit A bounded buffer is near overflow, or an unbounded buffer is growing toward memory pressure
featbit.buffer.items.dropped Items known to be lost through capacity, failed flush, or shutdown Missing Usage, Insight, or notification data without a process crash
featbit.buffer.flush.operations/duration/batch_size Flush outcome, elapsed time, and number of input items A slow or failing database prevents workers from keeping up
featbit.worker.running Whether each background loop is active A worker terminated and will no longer process work
featbit.worker.heartbeat.age Time since the loop completed an iteration, including an idle one The task still exists but is stuck or no longer making progress
featbit.worker.last_success.age Time since a successful non-empty flush Work is arriving but has stopped reaching persistent storage
featbit.worker.loop.failures Background-loop exceptions by bounded reason A recurring error is degrading or repeatedly interrupting processing

Only some of these buffers are bounded, so the applicable metric set differs by target.

BufferImplementationApplicable metrics
usage Bounded Channel with DropOldest in UsageTracker Full set, including capacity and drops
postgres_notification 1000-item bounded Channel with DropOldest in the ELS consumer Full set
insight Unbounded List<object> behind a lock in InsightsWriter Occupancy and flush metrics only
store_sentinel Worker with no buffer Worker metrics only

InsightsWriter cannot drop, so it grows until the flush keeps up or the process runs out of memory. Report its occupancy and alert on sustained growth; featbit.buffer.capacity and featbit.buffer.items.dropped are undefined for it until it is given a bound, which is a code change rather than instrumentation.

M5 answers: Is in-memory work accumulating? Are items being dropped? Can persistence keep up? Is a worker stopped or stuck? Could shutdown lose pending work?

How to implement

  1. Maintain atomic counts on enqueue, dequeue, and snapshot.
  2. Use the bounded-channel item-dropped callback .
  3. Count an unretried failed batch as dropped; record duration and size once per flush.
  4. Update worker heartbeat on idle iterations and last success only after a non-empty successful flush.
  5. Measure bytes only when already known .
M6 Required Low

Rate limiting and validation

Task goal

Observe all ELS rate-limit decisions—whether in-memory or Redis-backed—and classify Streaming validation results.

Why

Rejections reveal overload or limits set too low; Redis fail-open silently removes distributed protection ; validation results separate bad client input from a server dependency outage.

What to measure

MetricPurpose
featbit.evaluation_server.ratelimit.decisionsAll in-memory and Redis-backed allowed/rejected decisions; fail-open applies only to Redis
featbit.evaluation_server.streaming.validation.operationsAccepted, invalid, and unavailable results that distinguish client errors from dependency failures

How to implement

  1. Record exactly one outcome per limiter acquisition; avoid double-counting rejection.
  2. Instrument both Redis and in-memory limiters; separate fail-open from normal allow.
  3. Add a finite reason code to validation results .
  4. Record validation once and remove raw tokens, secrets, or query strings from logs and attributes.
A Required Operational

Alerts and Collector health

Task goal

Turn M1–M6 into dashboards and actionable alerts in the monitoring backend, and detect telemetry loss.

Why

FeatBit emits signals; Prometheus and Grafana aggregate and evaluate them over time . Collector self-metrics prevent a broken telemetry pipeline from making an unhealthy service appear quiet.

What to measure

AreaMinimum alert
StreamingAbnormal closes or unexpected connection change
MessagingFailure, known drop, stale consumer, or backlog above SLO
Flag ChangePublish without consume, fanout failure, or slow propagation
StoreAll providers unavailable or repeated failover
Buffer / workerHigh utilization, any drop, or stale worker
Rate limitAny fail-open
CollectorReceiver refusal, export failure, or queue saturation

How to implement

  1. Scrape application metrics on 8889 and Collector self-metrics on 8888 .
  2. Build dashboards in Grafana; evaluate alert rules in Grafana Alerting or Prometheus, using Alertmanager when Prometheus owns the rules.
  3. Use sustained conditions and deployment-specific SLOs rather than universal absolute thresholds.
  4. Do not alert on last_success.age alone .
  5. Verify that exporter failure never blocks FeatBit traffic.
T1 Optional Debug / sampled

Flag Change trace

Task goal

Locate a sampled propagation delay in persistence, publish, consume, or fanout.

Why

Metrics show that propagation is unhealthy; a sampled trace locates whether one Flag Change was delayed or failed in persistence, publish, consume, or fanout .

What to measure

persist→ publish→ consume→ fanout

Create one flag_change.fanout span for each Flag Change, covering the whole batch of WebSocket sends; do not create a span for every connection . The trace ends at the ELS socket-send boundary .

How to implement

  1. Propagate W3C trace context in the internal message envelope.
  2. Register the custom ActivitySource with OTEL_DOTNET_AUTO_TRACES_ADDITIONAL_SOURCES.
  3. Control and sample this trace separately from global tracing .
  4. No SDK participation is required .
FEATBIT_OTEL_CUSTOM_TRACES=flag_change FEATBIT_OTEL_CUSTOM_TRACE_SAMPLE_RATIO=0.05
✓ Definition of done

First iteration complete

  • M1–M6 are visible with bounded attributes.
  • No sensitive or unbounded identifier appears in metrics.
  • Gauge collection performs no I/O or connection scanning.
  • Failure scenarios trigger the intended alerts.
  • Exporter failure does not affect FeatBit availability.
  • Streaming and fanout show no material regression.
