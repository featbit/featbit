# Migration 2: Metrics and Experimentation Migration Plan for Kafka + ClickHouse Deployments (5.4.6 → 6.0.0)

## Conclusion and Scope

Kafka and ClickHouse do not contain 5.4.6 metric definitions, experiment metadata, or historical iteration results. Therefore, there is no `old ClickHouse table → new ClickHouse table` migration for this part.

- Kafka `featbit-insights` carries only exposure and metric events.
- ClickHouse `events` stores only event facts; Migration 1 handles it.
- The API Server's primary database stores `ExperimentMetrics`, `Experiments`, and `Iterations`.

The work for this plan is to run PostgreSQL or MongoDB Migration 2 according to the customer's actual `DbProvider`, then verify that the migrated control-plane data joins correctly to the ClickHouse events migrated by Migration 1. Do not reconstruct metric definitions, experiments, or historical results from Kafka messages or ClickHouse events.

## Data Objects Involved

| Data | 5.4.6 source | v6 target | Written to Kafka/ClickHouse? |
|---|---|---|---|
| Metric definition (PostgreSQL) | `experiment_metrics` | `release_decision_metrics` | No |
| Experiment (PostgreSQL) | `experiments` | `release_decision_experiments` | No |
| Iteration (PostgreSQL) | `experiments.iterations` JSONB | `release_decision_experiment_runs` | No |
| Migration audit (PostgreSQL) | Generated by migration | `release_decision_activities` | No |
| Metric definition (MongoDB) | `ExperimentMetrics` | `ReleaseDecisionMetrics` | No |
| Experiment (MongoDB) | `Experiments` | `ReleaseDecisionExperiments` | No |
| Iteration (MongoDB) | `Experiments.iterations[]` | `ReleaseDecisionExperimentRuns` | No |
| Migration audit (MongoDB) | Generated by migration | `ReleaseDecisionActivities` | No |
| Exposure / metric events | ClickHouse `events` | Two `release_decision_*_events` tables | Yes; handled by Migration 1 |

## Cross-Database Relationships

After both migrations complete, the following keys must match:

| v6 control-database data | ClickHouse v6 event field | Purpose |
|---|---|---|
| Metric `featbit_env_id` | Event `env_id` | Environment isolation |
| Metric `key` / experiment primary metric event | Metric event `event_name` | Find metric events |
| Experiment `flag_key` | Exposure `flag_key` | Find experiment exposures |
| Experiment variant `key` | Exposure `variation_id` | Assign control/treatment groups |
| Run observation window | `exposed_at` / `occurred_at` | Select the same statistical time range |
| Experiment/run environment | Both event types' `env_id` | Prevent cross-environment data mixing |

Continue to preserve 5.4.6 iterations' historical aggregate results as legacy results through PostgreSQL/MongoDB Migration 2. Never recalculate them automatically from migrated ClickHouse events or overwrite them.

## Execution Plan

1. Confirm the actual `DbProvider` from the API Server configuration; do not infer the primary database from the presence of ClickHouse.
2. Snapshot the primary database, ClickHouse, and Kafka offsets for the same migration window.
3. Run the appropriate database Migration 2 in order: metrics → experiments → runs → activities. In parallel or separately, use Migration 1 to migrate ClickHouse events. Validate both parts against the same environment, flag, variation, and event-name rules.
4. Configure the v6 API to continue storing control-plane data in the original primary database. Set `OLAPProvider=ClickHouse`, the correct `ClickHouse__HttpEndpoint`, and database so statistical queries read the new ClickHouse event tables.
5. Produce a joint report containing control-database migration counts, ClickHouse event migration counts, and every environment, flag key, variation ID, or metric event name that cannot be joined.

## Test Plan

Prepare at least one legacy experiment containing a Custom Conversion, Custom Numeric, PageView, or Click metric, with one completed iteration and corresponding ClickHouse events.

Core assertions:

1. Every field, count, legacy-result, and idempotency test from the applicable PostgreSQL/MongoDB Migration 2 passes.
2. Kafka and ClickHouse contain no new metric-definition, experiment, run, or activity tables/messages.
3. The v6 API lists migrated metrics and experiments; the UI opens legacy runs and labels them explicitly as imported legacy results.
4. For each experiment, corresponding flag keys, variation IDs, metric event names, and environment IDs exist in the new ClickHouse event tables; unresolved items appear in the report.
5. For the same observation window, v6 ClickHouse queries return the expected exposure/metric samples without recalculating or overwriting the legacy iteration result.
6. After cutover, create a test run and send new Kafka insight messages. Confirm that the new run reads statistics from ClickHouse while metric/experiment configuration continues to be written to the primary database.
7. Running both migration parts twice creates no duplicate records.

## Completion Criteria

The Metrics and Experimentation migration for a Kafka + ClickHouse deployment is complete only when primary-database Migration 2 and ClickHouse Migration 1 are complete, every cross-database key reconciles, API/UI legacy reads work, and the new-run smoke test passes.
